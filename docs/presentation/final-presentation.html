Pratham collects millions of handwritten Hindi responses yearly. Every response must be manually transcribed before analysis — slow (~50 pages/person/day), expensive, and a barrier to timely educational intervention.

Why Tesseract fails

Designed for printed text. No handling of Devanagari matras, ligatures, or variable handwriting density.

Why Google/Amazon fail

English-centric models. Indic handwriting is out-of-distribution. Not fine-tunable for ASER vocabulary.

Why LLMs fail at scale

Opus-class: partial capability but 15× cost vs fine-tuned. Haiku 4.5: 0% accuracy on our 121-crop eval.

05 / 25
Why Devanagari Handwriting is Hard

1 — Matra attachment

Vowel diacritics (matras) attach above, below, and around the base consonant. No consistent position — above for आ (aa), below for उ (u), hanging right for ि (i). Generic detectors crop them out or merge adjacent words.

2 — Ligature fusion (conjuncts)

Two or more consonants fuse into a single glyph (e.g., क्ष, त्र, ज्ञ). The fused form looks nothing like either constituent. Segmentation at the character level is unreliable.

3 — Writer variability

Our 121-crop eval spans 11 writer groups: CER ranges 21% (folder 38, neat print) to 100% (folder 37, erratic). The same word looks completely different across writers — no single template works.

4 — No clear word boundaries

Hindi uses a shared shirorekha (top bar) running across letters. Matras extend vertically above/below the line. Whitespace signals are weak and inconsistent in handwritten text.

Known failure mode: matra-aware box merge over-merges adjacent words on ~3.1% of dense rows. Documented in detection/postprocess.py; v3 fix candidate: per-row spacing histogram before merge decision.

What "matra-aware" means for YOLO v2

Devanagari matras hang above and below the base line, causing standard NMS to either (a) absorb the matra into the wrong word box or (b) assign a dangling matra its own erroneous box. v2 addresses this via:

  • Higher box loss weight (10.0 vs 7.5) — forces tighter box regression
  • Tighter NMS IoU (0.42) — less merging at detect time
  • Post-inference merge heuristic (horizontal gap + vertical overlap) — see slide 11

Failure mode: over-merging

merge_gap_px=8.0 is tuned for standard ASER layouts. On dense handwriting where two words are written close together, the merger can combine them into one box. Measured rate: ~3.1% of rows in internal audit.

v3 mitigation: compute per-row median inter-word gap before setting the merge threshold dynamically.

TrOCR Modelling — Architecture Deep-dive

Model: VisionEncoderDecoderModel

ComponentConfiguration
EncoderViT-base-patch16-224-in21k (ImageNet pre-trained)
Patch size16×16 pixels, 196 patches per image
Hidden dim768-d, 12 transformer heads
DecoderRoBERTa-Hindi (flax-community/roberta-hindi)
TokenizerHindi BPE — knows Devanagari subwords, matras, conjuncts
Cross-attentionEncoder CLS + patch tokens → decoder cross-attn
GenerationBeam search, beam=2, max_length=64

Why these choices?

  • ViT patch-based: captures long-range matra dependencies across full word width; CNN conv filters miss long-range context
  • RoBERTa-Hindi decoder: BPE subwords include matra+base combinations — far fewer UNK tokens than generic tokenizers
  • Encoder-decoder (not CTC): allows variable-length output naturally; CTC requires explicit blank symbol and struggles with conjunct sequences

Training configuration (v1)

HyperparameterValue
OptimizerAdamW
Learning rate5e-5 (cosine decay)
PrecisionFP16 (halves GPU memory)
Batch size16 (Tesla T4 15GB)
Max steps~42,000 (stopped at 38,000 — best)
EvaluationEvery 2,000 steps
Input preprocessingTensor cache (offline ViT resize+normalize)

Offline tensor caching reduced training wall-clock time by ~40% by avoiding repeated ViT preprocessing.

Key design decisions

  • fliplr=0 in augmentation — flipping invalidates Devanagari glyphs
  • FP16 enabled — 1.5× speed gain on T4
  • Word-level (not line/page) — avoids line segmentation which is harder for cursive Hindi
  • Preprocessed tensors — scalable to 95K+ images without memory issues

Curriculum design

  • Phase 1 (early batches): mix 80% HindiSeg + 20% Pratham with minimal augmentation — preserve recognition capability
  • Phase 2 (later batches): increase Pratham ratio + apply recognition/augment.py (ink-fade, elastic warp, paper-noise) — build robustness
  • Lower LR (5e-6 vs 5e-5): avoids catastrophic forgetting of HindiSeg vocabulary

Data: the 240-crop set

  • Drawn from annotation_history_ubuntu.csv (881 rows)
  • Filtered for completeness (non-empty label + non-INVALID status)
  • Augmented 3× via recognition/augment.py for effective size ~720
  • Entrypoint: recognition/train_v2_domain_adapt.py --train-csv ...

Limitation: 240 crops is a small set relative to HindiSeg (69k). Modest gain on field reflects data scarcity; more annotation would unlock larger gains.

Text Post-processing — Three-stage Pipeline

Stage 1 — Unicode NFC

recognition/postprocess/unicode_normalize.py

Applies unicodedata.normalize("NFC"). Devanagari has many canonically-equivalent sequences (e.g. precomposed vs decomposed matras) — different annotators encode the same word differently.

Contribution: ~−1.7pp CER on eval pages. Cheapest, most reliable win in the project.

Enabled for all scenarios (eval + field).

Stage 2 — Char 3-gram LM Rescoring

recognition/postprocess/lm_rescore.py

Character n-gram language model scores the TrOCR hypothesis against alternatives from the decoder beam. Corpus: HindiSeg transcripts by default.

Contribution on eval pages: ~−1.4pp CER.

Field regression: +0.6pp CER — HindiSeg corpus skew causes the LM to prefer HindiSeg-style predictions over field-style handwriting.

Shipped disabled for field: LM_ENABLE_FIELD=false (default).

Stage 3 — ASER Dictionary

recognition/postprocess/dictionary_correct.py

Greedy Levenshtein-1 correction against a ~4,200-word ASER vocabulary. If the TrOCR hypothesis is not in vocab but a vocab word is within edit distance 1, substitute.

Contribution: ~−0.7pp CER on eval pages (limited — eval pages span broad vocabulary beyond ASER scope).

Combined with NFC for field: ~−1.9pp total.

Key takeaway: post-processing is scenario-dependent

The same post-processing stack helps eval-page text but hurts field text (LM component). v2 ships with env-var controlled scenario flags: V2_SCENARIO=eval_pages|field in pipeline/scripts/pipeline_v2.py. This is a known design gap — v3 should build an in-domain LM or switch entirely to a language-model-aware decoder.

LM regression: why it happened

The char 3-gram LM was trained on HindiSeg transcripts. Field handwriting uses different vocabulary and spelling conventions. When a plausible alternative from the decoder beam scores higher in the HindiSeg-biased LM, it replaces a correct field prediction with a wrong one. Net effect: +0.6pp CER. Failure Modes — What Didn't Work

1. LM rescoring on field regressed CER by 0.6pp

HindiSeg corpus skew. Shipped disabled for field (LM_ENABLE_FIELD=false). v3: rebuild LM on in-domain transcripts or remove entirely.

2. Annotation kappa 0.62 — below 0.8 target

Only 180/881 portal entries had dual annotations. Gold set: 140 rows vs 400 hoped. Limits domain adaptation data quality.

3. Pratham field word-exact ~12% — not production-ready

HITL mandatory for all field uploads. Not a feature — a deployment constraint. Target was >40% for unattended use.

4. YOLO over-merge ~3% dense rows

Matra-aware merge gap fixed at 8px. Over-merges adjacent words when horizontal gap is below threshold. v3 fix: per-row dynamic gap from spacing histogram.

5. TrOCR HindiSeg gain modest (1pp)

Checkpoint step 38k was already near saturation. Curriculum + augmentation gave less than the 3pp hoped for. More data would be needed to improve further on this distribution.

6. Monitoring uncalibrated; HITL 3× not 8×

SLOs are placeholders. HITL throughput bottleneck is per-word review UX latency, not model speed.

Deployment & Ethics

Deployment constraints (v2)

  • HITL is mandatory for field uploads — word-exact accuracy ~12% means direct grading from model output would be harmful to students
  • LM rescoring off by default for field; any change requires re-running ablation on field data

Ethical considerations

  • Student data sensitivity: ASER responses are from rural children. Data must follow Pratham's data-handling agreements — no sharing with third parties, no public release of raw images
  • No automated grading without review: model errors that reduce a student's score unfairly are worse than slow manual grading. HITL gate is not optional
  • Annotator bias: 881 rows from a single Ubuntu deployment; kappa 0.62 suggests label noise. Domain adaptation trained on this data inherits annotation inconsistency
  • Script sensitivity: Devanagari is a sacred script in many Hindu traditions — misrecognition should not reach end-users without review

What "production-ready" requires

  • Field pipeline CER below 50% with HITL coverage (v2: 71.3% — not there yet)
  • Cohen's kappa > 0.8 on gold-set labels for trust in domain-adapt data
  • Live monitoring calibration on real ATM traffic
  • Formal sign-off from Pratham ops team on SLOs
